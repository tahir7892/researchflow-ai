# Evaluation plan — ResearchFlow AI

## Integrity note
All publication-record test fixtures are synthetic. `observed_unit_tests.json` is generated by executing mocked unit tests. **It is not evidence of live OpenAlex/Crossref availability, Gemini free-tier access, business productivity gains, or user adoption.** Do not make those claims until the relevant tests have actually been performed.

## User and baseline assumptions
Target user *assumption*: a small marketing/research analyst responsible for a weekly research scan, normally searching two sources, manually removing duplicate results and assembling a sourced brief and checklist. The job-to-be-done is to create a trustworthy and reviewable brief quickly. Interview one real or proxy user if possible; replace assumptions with notes as evidence. Do not invent interview quotes.

**Manual baseline procedure:** Ask the same user to search OpenAlex and Crossref manually for an agreed topic and publication date range. Time from starting research to producing a brief and checklist. Record minutes, duplicate papers missed, broken/missing sources, human edits, and an independent review pass/fail under the rubric below. Use the same topics with the app and time from topic entry through approved export (including review and retries). Two or more representative cases are preferred for time comparisons; all 10 cases should be evaluated for functional quality.

## 10-case acceptance suite
See `test_cases.csv`: typical cases, input variation, edge cases, partial outage, full outage, invalid model response, fabricated reference and non-developer export. Run `python scripts/run_checks.py` for mocked unit checks. Then execute the live UI cases and fill `baseline_and_results_template.csv`; unit checks alone do not complete the assignment.

## Pass/fail rubric for an approved brief
- **Source provenance:** Every source ID actually exists in the retrieved set; no invented bibliographic entry.
- **No unsupported findings:** Statements of empirical conclusions must be checked against abstracts/full text; titles alone cannot establish results.
- **Completeness:** Relevant topic, at least one evidence item, follow-up actions, limitations, source links.
- **Safety:** The run remains editable, is never externally published before approval, and has a timestamped audit record.
- **Reliability:** One provider failing produces partial output + warning; both failing produces a failure rather than fabricated content.
- **User experience:** Proxy user can run, review and export without reading Python code, aided by README.

Scoring: each criterion pass (1) or fail (0) per applicable case; record n/a where not applicable, plus root cause. Do not report percentages until evaluated.

## Required failure analyses
1. **Provider outage:** Source error (timeout/429/5xx) → retry and partial retrieval; both unavailable → explicit failure. Check source health.
2. **AI hallucinated citation:** Generated ID outside provided set → reject before display; degraded outline labelled; tighten prompt.
3. **Invalid/malformed model JSON:** Parser/schema validation rejects malformed output → offline outline + warning; model selection and retries can be improved.

For each, capture reproduction steps, observed behavior, underlying cause, fix and regression test outcome. Current tests simulate these behaviors; live incident logs must be recorded separately.

## Quantitative metrics
- **Elapsed task time:** Include researcher review time, API processing, error recovery and final approval. Use stopwatch.
- **Correctness:** `% of applicable rubric checks passed` = passes / applicable checks × 100.
- **Human interventions:** Count manual corrections, failed requests and approval actions. Approval is always mandatory.
- **Reliability:** Successfully generated and approved briefs / attempted briefs on live 10-case test set.
- **Cost:** Log API tier and any actual cost. Do not infer all API use is permanently free.

## Decision criteria
Target (not a claimed result): median end-to-end time at least 30% lower vs manual baseline, source correctness ≥95%, zero unapproved external publication, explicit graceful failure. If the system misses a target, report that plainly. A small evaluation sample is directional evidence, not a statistically significant business ROI estimate.

## Two-week adoption instrumentation (future plan)
Week 1: ask target/proxy user to produce three briefs; track start/end time, approval edits, incorrect citations and blocked requests. Week 2: repeat on new topics; review feedback, quality and manual effort, propose fixes. If the project ends before deployment, mark these as future plans rather than collected data.
